# CodeMate 原生化：agent 提示词套件 v2

> 版本：v2.1（2026-10-15）。v1、v2 见本文件的 git 历史。
> 用途：内部 agent team，模型路由为 `glm52-main`、`glm51-critic`、`qwen-security`（见第七节）。
> 来源：v1、Codex 版提示词、同事交接文档的使用要求（交接文档本身在内部，本文未读到其内容）。
> 第八节「复核线索」是在社区 Code OSS 1.113.0 上核查的结果，不是 vscode-internal 的事实；agent 必须在内部代码上复核后才能引用。

## 一、版本变化

### v2.1（2026-10-15）

负责人确认 VS Code MCP 基于社区 `test/mcp`，增加了自动录屏和一些操作。据此更新了 A1、A5、5.4、5.5、5.7、6.6 和第八节，社区版本的评估见本目录 06。宪章没有改动。

### v2（2026-10-14）

**新信息带来的改动**

- 交接文档：首轮最先做的工作改为交接核验，逐条判定「已证实 / 部分证实 / 与当前版本不符 / 待验证」，并新增交接核验表模板。
- 模型路由：按 `glm52-main`、`glm51-critic`、`qwen-security` 重写分工；删除 v1 中的温度、推理开关建议和 Qwen Plus。

**吸收 Codex 版的内容**

- 「原生」的口径：DOM 集成不等于 webview；去掉 webview 不要求取消所有 IPC 和扩展宿主职责；换成 iframe 不算完成；Shadow DOM 不是安全隔离，Trusted Types 也不会自动清洗内容。
- 性能按 8 段拆分；不预设 webview 是主要瓶颈；检查成本是否只是挪到了主线程、首次打开或首次请求。
- 完成度分 7 级，报告时写明分母和未知项，不合成一个百分比。
- 基线增加「基座不含 CodeMate」，并注明「禁用」不等于去掉打包和初始化成本；明确计时边界、跨进程时钟校准、MCP 计时误差、样本数与尾延迟。
- 阶段 A–D 与最小端到端试点；路线结论四选一，并附最强反证。
- 决策边界：可逆的工作自主推进，重大取舍再请负责人决定。
- 并发：worktree、desktop 实例、端口、用户数据目录、kernel 会话都要登记归属；分歧用实验解决；模型不可用或平台不支持并行时如实说明。
- 会话交接六项、按风险选择验证、不覆盖他人改动、内部资料不外发。

**相对 Codex 版的调整**

- 拆成「宪章 + 阶段任务 + 角色说明 + 模板」。Codex 版是一整段，子 agent 和后续每次会话都要带上首轮任务和全部背景，篇幅大、重点分散。
- 长段落和「既不…也不…」式的表述，改成可以逐条检查的条目。
- 补齐 8 个模板和 9 个角色的检查清单，便于多个 agent 输出一致、总控汇总。
- 写明 `qwen-security` 的触发条件，以及进入阶段 C 需要负责人确认。
- 不依赖外网链接。在社区代码上核查到的实现细节放进第八节，标明不是内部事实，但保留具体位置，节省调查时间。

**对 v1 的修正**

- 1.113 上的实现细节（服务注册方式、contribution 阶段、具体命令）从「硬约束」降为复核线索。
- 回退方式、任务粒度、验证组合不再写死，按工程现状和改动风险决定。
- AI 功能的性能主要与原插件比较；社区版只用于衡量基础启动开销，并作参考。

## 二、使用方式

把本文件放进内部仓库，并填写两个占位符：`{{KIT_PATH}}` 是本文件在内部仓库中的位置；`{{WORKSPACE_DIR}}` 是留痕目录，交接文档或现有规范有约定时沿用，例如 `analysis/codemate-native/`。

| 场景 | 提示词组成 |
| --- | --- |
| 首次启动总控 | 三、宪章 + 4.1 首轮任务 |
| 负责人确认路线后 | 三、宪章 + 4.2 阶段 C + 5.1 总控 |
| 进入整体回归 | 三、宪章 + 4.3 阶段 D + 5.1 总控 |
| 派发子 agent | 三、宪章 + 第五节对应角色 + 任务卡 + 必读输入清单 |

宪章修改后，同步到所有 agent 并更新版本号，避免不同 agent 按不同版本工作。

## 三、项目宪章 v2（所有 agent 共用）

```text
# CodeMate 原生化项目宪章 v2

## 1. 目标与现状
- 目标：在内部基座 vscode-internal 上，CodeMate 不再用插件 webview 承载界面，改为在 Workbench 内原生集成；在可比较的环境中，desktop 的基础启动和运行指标接近社区 VS Code，AI 功能的加载、响应和运行体验明显改善。
- 组成：CodeMate-VSCode（插件侧代码）、CodeMate-WebView（webview 界面代码）、kernel 工具集成（AI 交互依赖它）、vscode-internal（基座，实际落地和验收对象）。
- 现状：同事已开展迁移，据统计约 65 万行；交接文档为 analysis/CodeMate原生DOM集成-交接文档.md。行数不代表完成度，口径需要核实。
- 本套件的阶段任务、角色说明、模板和复核线索见 {{KIT_PATH}}。

## 2. 产品约束（不得自行放宽）
1. 不使用插件 webview 承载 CodeMate 界面，也不能换成等价的 iframe 容器。
2. 界面、UI、交互和用户可观察的功能行为与原实现一致；已知差异必须登记，不得以原生实现的限制为由静默删减。
3. 保留 AI 与 kernel 集成能力。
4. 保持必要的权限、故障隔离、用户状态兼容和可维护性。
5. 内部源码、资料和凭证只在内部环境处理，不发送到未授权的外部服务或模型。

## 3. 统一口径
- 原生：界面以 Workbench 内的 DOM 和组件形式集成，不是操作系统原生控件；「仍使用 DOM」不等于「仍使用 webview」。是否保留 Vue、如何挂载、如何接入基座服务，由路线评审决定。去掉 webview 不要求取消所有 IPC、消息协议或扩展宿主职责，但关键路径上的每次跨进程通信、每次等待扩展激活，都要写明职责理由并有测量数据。
- 完成度等级（盘点和汇报统一使用，每一级都要有对应证据）：
  L0 仅复制或改写了代码
  L1 已接入构建：产物中存在（附构建记录）
  L2 已接入运行：运行时被加载或调用（附日志或打点）
  L3 主流程可用（附端到端场景记录）
  L4 异常路径可用：错误、取消、重试、重连（附场景记录）
  L5 功能与界面一致性已验证（附新旧对照证据）
  L6 性能与集成验收通过（附集成版本上的测量）
- 结论标签：【事实】已验证，附证据；【推断】有依据，写明依据；【假设】待验证，写明验证方法；【待决定】需负责人决定，写明选项和影响。
- 证据：关联到提交、补丁、文件与符号、命令与输出、日志、截图或测试结果。代码、依赖或环境变化后，判断证据是否失效，重跑受影响的部分。

## 4. 工作原则
1. 先接续再补缺：先核验交接成果并复用有效部分。没有证据时，不推倒已有成果，也不因投入巨大就默认路线正确。
2. 先理解再迁移：存量审计和路线验证完成前，不继续批量迁移。
3. 先测量再优化：不预设 webview 是唯一或主要瓶颈；检查迁移是否只是把工作挪到了 Workbench 主线程，或把启动时的等待挪到了首次打开、首次请求。
4. 以当前代码和运行结果为准：分析文档、交接文档和参考资料中的技术判断，都要记录适用版本，并在当前代码上核实。
5. 是否拆包、何时加载，以实际构建入口、导入图、打包产物和运行时加载记录为准，不能只看源码里有没有 import()。
6. 不为形式上的原生化引入不必要的复杂度；优先复用基座已有能力，并写明复用或不复用的理由。
7. 任务按行为闭环拆分：一个任务要能在一个会话内完成并验证，做不到就拆小。
8. 验证按风险选择：以内部仓库的脚本和 CI 为准；区分历史失败和新增失败；不为每个小改动机械执行全部昂贵检查；集成后在集成版本上执行受影响的验证。
9. 不仅凭构建成功、截图、mock 或 agent 自述宣称完成；无法运行验证的部分标为「待运行验证」，不能用文档审查代替。
10. 不覆盖、不回退他人的未提交改动。
11. MCP 能力不足时，不暂停全部验证：能用现有测试、CLI、日志、调试器或性能工具完成的继续做；缺口写成 MCP 需求单。可以按需安装 skill 或工具，先检查来源、适用性和依赖影响，并记录。

## 5. 决策边界
- 自主推进并记录：可逆的调查、诊断、实验和测试；已授权范围内的修复和工程选择。ADR 用来记录决定，不等于每项都要审批。
- 先给出方案、证据和影响，再请负责人决定：改变目标或约束；不可逆的数据操作；削弱权限或隔离边界；未授权的发布；路线级取舍（保留还是替换已迁移的主体设计）；进入阶段 C。
- 遇到访问或运行阻塞：只暂停相关的依赖链，继续其他可做的工作，准确说明缺少什么，不虚构结果。

## 6. 团队与并发
- 角色、agent 实例和模型分开。模型路由：
  glm52-main → GLM-5.2-Auto(Volcano-MaaS)：总控，以及交接与盘点、架构审查、性能、验证、实施、工具等执行角色
  glm51-critic → maas-glm-5.1-zhipu：独立评审路线、接口、改动和完成证据
  qwen-security → Qwen3.7-Max-Auto（BaiLian-MaaS）：安全边界和高风险架构的补充复核
  先确认平台实际支持的调用方式、上下文长度和参数；不添加未列出的模型，不假设温度或推理开关。
- 实现与评审使用独立上下文。glm51-critic 与 glm52-main 同属 GLM 系列，不称为跨系列审查；命中安全或高风险架构条件的事项，加做 qwen-security 复核。
- 总控负责统一目标、接口、依赖、派发、集成和最终结论；必须亲自复核关键证据、处理分歧，不能只拼接子 agent 的总结。
- 派发子 agent 时提供：本宪章、对应的角色说明、任务卡、必读输入清单。先并行调查；接口稳定后再并行修改。
- 归属：同一时间，每个文件或共享接口只有一个修改负责人；并行修改使用独立 worktree，并写明集成顺序；desktop 实例、端口、用户数据目录和 kernel 会话也要登记归属。
- 流程：领取 → 执行与自测 → 独立评审 → 集成 → 受影响验证 → 更新状态。评审要读需求、diff、接口契约和原始证据，并复现与风险相关的检查。
- 分歧用代码或实验解决，不用模型投票。同类尝试连续两次没有新证据，就换方法、缩小任务或升级诊断。
- 某个模型暂不可用时：记录缺失的评审覆盖，继续可做的工作，不虚报调用或通过。平台不支持真正的并行或模型选择时：说明限制并顺序执行，不把顺序执行描述成团队并行。

## 7. 留痕
- 位置：优先沿用交接文档或现有规范指定的目录；没有时使用 {{WORKSPACE_DIR}}。保留已有分析和交接原件；不在多个目录维护互相矛盾的状态。
- 至少维护以下内容（可以合并成更少的文件）：
  README：目标、约束、阅读顺序、文档索引
  STATUS：当前阶段、有效版本（仓库 / 分支 / 提交）、进行中、阻塞、下一步
  交接核验表：交接声明 → 当前代码与入口 → 验证方式 → 核验结果 → 后续任务
  架构与调用链：现状、目标、旧实现到新实现的映射
  功能与消息对照：入口、调用链、handler、完成度等级、差异、用例、证据
  性能记录：环境、方法、基线、目标（已认可 / 待确认）、实验
  决策记录（ADR）：问题、备选、证据、结论、后果
  任务卡：优先级、依赖、负责人、范围、验收、结果
  工作日志与交接：完成内容、失败尝试、现场、续作方法
- 任务卡保存详细状态；STATUS 只做汇总和引用，由总控统一更新。完成有意义的检查、改动或决策时记录，不需要每读一个文件就写日志；大日志和性能产物按现有规范存放，文档只保留索引。
- 会话开始：读 README、STATUS 和本次任务卡，核对现场（分支、提交、未提交改动、运行中的进程）是否与记录一致；不重复全仓分析，不只依赖聊天历史。
- 会话结束或上下文接近上限时，写交接：
  1. 仓库、worktree、分支、提交和未提交改动；
  2. 当前任务，以及已验证的部分；
  3. 证据位置和关键决定；
  4. 未完成事项、失败尝试和已排除的假设；
  5. 活跃的进程、测试实例和资源归属；
  6. 接手者的下一步：具体操作、命令和预期结果。

## 8. 汇报
- 使用中文。先报告结果、证据和限制，再说下一步；详细资料写进文档，对话中给出路径。
- 完成度要说明分母、验证范围和未知项；代码量、接线数量、功能验收率分开报告，不合成一个百分比。
- 不用迁移行数、文档数量或 agent 数量代替实际成果。
```

## 四、阶段任务

### 4.1 首轮：阶段 A，并准备阶段 B（发给总控）

```text
# 首轮任务：完成阶段 A（现场勘察与存量审计），并尽量完成阶段 B（路线验证与最小端到端试点）所需的准备

要求：本轮实际完成检查、索引、运行验证和最小实验，不只给计划。只做调查、运行验证和必要的最小诊断改动（打点、日志、脚本），不做大范围重构，不继续批量迁移。能并行的调查拆成任务卡派给子 agent；交接核验和路线判断由你负责，并复核关键证据。

A1 现场与工具
- 记录仓库、分支、提交、未提交改动、构建与运行方式、内部规范和 CI 入口。
- 核实 VS Code MCP（zyh/ai-research，提交范围 850e0aa8fcf9a94fc842812924b29b351ccf72e1 → 28356318c067d58bcd89d6857c44db85710ad305；基于社区 test/mcp，增加了自动录屏等操作）：相对社区版本的改动、实际工具清单、连接方式，以及启动方式（源码还是构建产物、启动参数、用户数据目录）。用一次冒烟证明可用：启动 → 打开 CodeMate → 截图 → 用脚本读取一个打点或 DOM 状态 → 读取控制台消息 → 停止，并找到录屏和日志。不假设已连接或具备未验证的能力；缺口写成 MCP 需求单。
- 检查是否已有 STATUS、任务清单、ADR、性能记录或后续交接；确认版本和有效性，避免重复劳动。

A2 交接核验（最先完成）
- 读取 analysis/CodeMate原生DOM集成-交接文档.md，提取：架构与设计理由；已完成的功能与接入链路；已通过的构建、测试和运行场景；临时兼容层、绕行方案和未清理的代码；未完成事项、已知问题和风险；启动方式、环境依赖、分支与提交；推荐的后续顺序。
- 逐条填写交接核验表。每条「已完成」「已解决」的声明，判定为已证实、部分证实、与当前版本不符或待验证，并附证据。有效成果直接复用；有疑问的回到代码和实验确认，不凭措辞判断。

A3 已有分析
- analysis/codemate-plugin、analysis/y00564605-codemate-dom、analysis/ai-native-migration：先读索引、结论和与当前问题相关的章节，再按需深入；不把「读完全部材料」当作开工前提。
- 记录每份资料的适用版本、过期内容、相互矛盾之处，以及与当前实现不一致的地方。

A4 存量审计
- 65 万行的口径：区分业务代码、复制代码、生成物、第三方依赖、测试和未接入运行的代码；统计用脚本完成并保存，可以重复运行。
- 旧实现到新实现的映射：入口、依赖、调用链、消息协议、handler、缺失部分、重复实现、残留旧路径；每项标完成度等级。
- 构建与加载：实际构建入口、导入图、打包产物和加载时机；服务初始化、contribution 阶段和界面恢复的真实调用关系；CodeMate 代码进入了哪些产物、各占多少体积。
- webview 原先提供的环境：主题、字体、默认样式、资源路径、状态保存、弹层和焦点；新实现由谁提供，缺了什么。
- kernel：运行位置、Node 与原生依赖、CPU 负载、通信方式、取消机制、故障传播。
- 执行位置：本地与远端场景下，文件、终端和工具操作在哪里执行。
- 信任边界：模型输出到 DOM、链接、命令和工具执行的每条路径如何清洗和授权。注意：Shadow DOM 不提供安全隔离；Trusted Types 只拦截不安全的写入，不会清洗内容。
- 结构风险：循环依赖、重复服务、全局状态污染、生命周期泄漏。
- 死代码：搜索不到调用或测试未触发，只能作为候选线索；删除前核验动态注册、平台与配置分支、兼容契约和覆盖范围。

A5 基线（先冒烟和小样本排错，再按波动和决策需要增加样本）
- 对照对象：①版本与构建条件尽量匹配的社区 VS Code；②内部基座不含 CodeMate（如果只能「禁用」，写明仍保留了哪些打包和初始化成本）；③原插件方案；④当前迁移方案。可获得时，社区 Chat 场景作为额外参考。社区用于衡量基础启动开销；AI 功能主要与原插件比较。无法获得的对照写明原因和影响。
- 分段测量：desktop 进程启动与窗口显示；Workbench 恢复与可交互；插件发现、加载与激活；CodeMate 模块加载、初始化与界面首次打开；kernel 启动、连接与就绪；AI 请求发出 → 网络首字节 → 首段有效内容 → 实际绘制；流式渲染、输入响应、长会话与大内容；关闭重开、状态恢复，以及适用的多窗口场景。分析关键路径上的同步阻塞、过早初始化、重复加载、跨进程通信、资源加载、渲染和内存问题。
- 固定或记录：硬件、操作系统、版本、补丁与构建模式；用户配置、扩展、工作区与窗口恢复状态；冷启动、热启动及具体缓存条件；kernel、网络、模型服务和后台负载；样本数量、计时边界和测量方法。
- 本地开销与外部服务延迟分开；必要时用回放或模拟服务，但保留真实 kernel 与服务的集成验证。不同进程的时钟未经校准不能直接相减；MCP 轮询计时要注明误差。报告原始数据、中位数和波动；样本不足时不报告尾延迟。
- 核实测量时的启动方式：社区 test/mcp 启动的实例处于开发模式、关闭了 V8 代码缓存、开启了 tracing（录屏时还要编码视频），数据不代表用户使用的构建。启动和加载性能用生产构建、固定参数测量；运行期指标在页面内打点后读取；各对照对象的启动方式保持一致，并写进性能记录。
- 「与社区对齐」的指标和允许差距，在取得基线后提出建议，并标明已认可和待确认；目标确认前只报告测量结果和改善幅度，不宣称达标。

A6 路线初判
- 逐项判断：是否满足不使用插件 webview 的约束；是否改善了已测量到的瓶颈；模块边界、进程职责和服务依赖是否合理；是否正确复用基座能力；是否改变了权限、隔离和故障传播边界；是否保留了旧功能和用户状态；对社区升级、构建、维护和回归测试有什么影响。
- 对关键设计给出「保留 / 调整 / 替换 / 暂缓」建议，附证据和最强反证。utility 进程、Shadow DOM、服务注册方式、懒加载策略等都是待验证的候选方案，不预设为唯一答案。
- 约束与性能、兼容性或维护目标冲突时，写清冲突、备选方案和需要负责人决定的事项，不自行放宽目标。

B 最小端到端试点（本轮完成准备；条件允许就执行）
- 选一条代表性流程：打开 AI 界面 → kernel 就绪 → 提交请求 → 流式展示 → 工具调用或取消 → 状态恢复。可以拆成关联的子场景，避免一个外部阻塞让全部验证停下。

- 列出哪些工作可以继续，哪些必须等待架构决定。
```

## 七、模型路由

| 路由别名 | 内部模型标识 | 默认职责 |
| --- | --- | --- |
| `glm52-main` | `GLM-5.2-Auto(Volcano-MaaS)` | 总控；交接与盘点、架构与构建审查、性能、验证、实施、工具 |
| `glm51-critic` | `maas-glm-5.1-zhipu` | 独立评审：路线、接口、改动和完成证据 |
| `qwen-security` | `Qwen3.7-Max-Auto（BaiLian-MaaS）` | 安全边界与高风险架构复核（触发条件见 5.9） |

- 分工不代表能力排名。角色、实例和模型分开：同一模型可以同时跑多个角色实例，但实现与评审使用独立上下文。
- `glm51-critic` 与 `glm52-main` 同属 GLM 系列，可能有相同的盲区。`qwen-security` 是唯一的跨系列视角，所以路线结论、架构级 ADR 和最终验收至少经它复核一次；日常评审默认由 `glm51-critic` 完成，避免 `qwen-security` 成为瓶颈。
- 上下文长度、温度、推理模式、并发数等参数，先在平台上确认再使用；不确定的不要写进配置。
- 配置中的标识要逐字一致：`GLM-5.2-Auto(Volcano-MaaS)` 用半角括号，`Qwen3.7-Max-Auto（BaiLian-MaaS）` 用全角括号。

## 八、复核线索（社区 Code OSS 1.113.0，非内部事实）

以下内容只作为调查起点。vscode-internal 的版本可能不同，引用前必须在内部代码上复核，并标注版本。

**构建与加载**

- 生产打包（`build/lib/optimize.ts`、`build/next/index.ts`）使用 esbuild `bundle: true`，未开启 `splitting`：`src/vs` 内相对路径的 `import()` 会被内联进同一个入口包（如 `workbench.desktop.main.js`），不会拆出单独的文件。
- 同一配置使用 `packages: 'external'`：对 `node_modules` 的裸模块导入不会打进入口包。社区代码在渲染进程中常用 `src/vs/amdX.ts` 的 `importAMDNodeModule` / `resolveAmdNodeModulePath` 加 `FileAccess.asBrowserUri`（`src/vs/base/common/network.ts`）按需加载；开发态的 import map 只用于 CSS（`src/vs/code/electron-browser/workbench/workbench.ts`）。需要核实 Vue 和组件库在 vscode-internal 中实际如何构建和加载。
- 主入口 `src/vs/workbench/workbench.desktop.main.ts`、`workbench.common.main.ts` 静态引入各 contribution。
- 服务注册 `registerSingleton(…, InstantiationType.Delayed / Eager)`；contribution 阶段 `WorkbenchPhase.BlockStartup / BlockRestore / AfterRestored / Eventually`（`src/vs/workbench/common/contributions.ts`）。
- V8 代码缓存：`src/main.ts` 的 `getCodeCachePath` 在传了 `--no-cached-data`、设置了 `VSCODE_DEV`，或 `product.json` 没有 `commit` 时返回空，窗口随之使用 `v8CacheOptions: 'none'`（`src/vs/platform/windows/electron-main/windowImpl.ts`）。要确认内部构建的 `product.json` 带有 `commit`。

**性能工具**

- `npm run perf` → `scripts/code-perf.js` → `@vscode/vscode-perf`：`--build`、`--runs`（默认 10）、`--duration-markers <a-b>`、`--prof-append-timers`、`--disable-cached-data`（关闭 V8 代码缓存）。
- 计时服务（`src/vs/workbench/services/timer/browser/timerService.ts`）只在 Restored 阶段采集一次渲染进程打点，所以 `--duration-markers` 测不到启动之后才发生的打点，比如打开面板、发送请求。这类打点要在渲染进程中用 `performance.getEntriesByType('mark')` 读取（`vs/base/common/performance` 在渲染进程使用原生 `performance.mark`）。
- 启动打点 `code/willStartWorkbench`、`code/didStartWorkbench`、`code/willLoadExtensions`、`code/didLoadExtensions`、`code/willRestoreEditors` 等，以及 `ellapsed*` 系列指标。
- 命令：Developer: Startup Performance（`perfview.show`）、Developer: Show Running Extensions（`workbench.action.showRuntimeExtensions`）、Measure Extension Host Latency（`editor.action.measureExtHostLatency`）；启动参数 `--prof-startup`。
- webview 中的打点使用它自己的时间基准，不能与 Workbench 打点直接相减。

**webview 注入的环境（迁出后需要由挂载点提供）**

- 默认样式：`src/vs/workbench/contrib/webview/browser/pre/index.html` 中的 `@layer vscode-default`（body 的字体、颜色和 `padding: 0 20px`，以及链接、`code`、`kbd`、滚动条、焦点框等）。
- body 类名 `vscode-light`、`vscode-dark`、`vscode-high-contrast`、`vscode-high-contrast-light`、`vscode-reduce-motion`、`vscode-using-screen-reader`，以及 `data-vscode-theme-kind`、`data-vscode-theme-name`、`data-vscode-theme-id` 属性。
- CSS 变量：`src/vs/workbench/contrib/webview/browser/themeing.ts` 注入 `--vscode-font-family`、`--vscode-font-size`、`--vscode-font-weight`、`--vscode-editor-font-*`、`--text-link-decoration`，以及全部颜色和尺寸变量。
- API：`acquireVsCodeApi()` 的 `postMessage`、`getState`、`setState`（同一文件）；资源地址转换 `asWebviewUri`（`src/vs/workbench/contrib/webview/common/webview.ts`）。

**安全与进程**

- `src/vs/code/electron-browser/workbench/workbench.html` 的 CSP 含 `require-trusted-types-for 'script'` 和 `trusted-types` 白名单（1.113 中没有 `vue`）。
- HTML 清洗：`src/vs/base/browser/domSanitize.ts` 的 `sanitizeHtml` 返回 `TrustedHTML`。
- 渲染进程沙箱：`src/vs/platform/windows/electron-main/windows.ts` 中的 `sandbox: true`。
- 进程与通信：`src/vs/platform/utilityProcess/electron-main/utilityProcess.ts`（`UtilityProcess`）、`src/vs/base/parts/ipc/electron-browser/ipc.mp.ts`（`acquirePort`）；社区较新版本的 `src/vs/platform/agentHost` 可作为独立 agent 进程的参考（见本目录 01）。

**VS Code MCP（社区 test/mcp，详见本目录 06）**

- 基于 `test/automation` 和 Playwright。一个 MCP 进程只管理一个实例，调用 `vscode_automation_start` 之前其他工具都处于禁用状态。通用操作是 `vscode_automation_window_*`，包括截图、无障碍树快照、按选择器操作、`window_evaluate`、`window_console_messages`；2026 年 2 月以前的版本通过 `@playwright/mcp` 提供同等的 `browser_*` 工具。
- 启动的实例不适合测性能：`test/automation/src/electron.ts` 固定传 `--no-cached-data`；`test/mcp/src/application.ts` 的 `getApplication` 即使传了 `--build` 也设置 `VSCODE_DEV=1`，窗口因此加载 `workbench-dev.html`，也不加载语言包；Playwright tracing 总是开启并截图。
- 默认不指定 `--user-data-dir`，使用开发版的共享用户数据目录；日志目录 `.build/vscode-playwright-mcp/logs` 在每次 MCP 进程启动时清空。多个 agent 并行时，需要各自的 MCP 进程、worktree 和目录（可以通过 `--electronArgs` 或 `vscode_automation_restart` 的 `extraArgs` 传入）。
- 选择器和 `window_evaluate` 只作用于主文档：Playwright 选择器能穿透开放模式的 Shadow DOM，但进不了 iframe。webview 是两层 iframe，旧插件界面只能截图、录屏和按坐标操作。
- 传 `--build` 时会先从 update.code.visualstudio.com 下载上一个稳定版，内网要传 `--stable-build`。`--remote` 用 vscode-test-resolver 模拟远程工作区。
