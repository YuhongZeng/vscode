# CodeMate 原生化：提示词 v3 的信息收集

> 日期：2026-10-15。
> 用途：顾问看不到内部资料。下面两段提示词在内部运行，产出一份脱敏的信息报告，用来把 [04-agent-prompt-kit.md](04-agent-prompt-kit.md)（v2）优化成 v3。
> 提示词一中「顾问目前已知的情况」来自本目录的 02、03，由内部 AI 逐条核对。

## 一、流程

1. 用 `glm52-main` 运行提示词一。它需要能读取 vscode-internal、交接文档、analysis 目录和 VS Code MCP 的代码；平台支持子 agent 时，会按 A2 做一次小试验。
2. 用 `qwen-security` 运行提示词二，复核报告中的敏感信息。它与 `glm52-main` 不是同一系列的模型，能提供独立的视角。
3. 负责人处理复核中拿不准的条目，补充标了【需负责人】的项（报告 L 节有汇总），确认后发给顾问。
4. 时间有限时，先完成 P0 项。如果已经用 v2 跑过一部分（例如首轮的 A1、A2），把结果写进 I1；实际运行的反馈对优化最有用。

## 二、信息的用途

| 信息 | 会影响提示词的哪部分 |
| --- | --- |
| A 平台 | 宪章放进规则文件还是首条消息；角色说明是否改成按需加载的 skill；阶段任务能否写成 WorkFlow；评审能否使用独立上下文；会话交接的频率 |
| B 模型 | 每段提示词的长度预算；针对实际出现的偏差补充约束；任务在三个模型间的分工 |
| C、D、E 交接、分析与代码 | 把首轮任务从通用清单改成针对现有实现的检查项；选定试点流程；列出需要优先验证的风险 |
| F 性能 | 基线任务的对照对象、指标和优先级 |
| G 验证工具 | 验证角色的具体操作步骤；预先列出需要补充的 MCP 能力 |
| H 决策与约束 | 路线评审的选项范围；决策边界和汇报节点 |
| I 运行经验 | 直接针对已出现的问题修改 |

## 三、提示词一：信息收集（glm52-main）

```text
# 任务：收集优化 agent 提示词所需的信息，输出脱敏报告

## 背景
我们准备用 agent team 推进 CodeMate 原生化：在内部基座 vscode-internal 上，CodeMate 不再使用插件 webview，改为在 Workbench 内原生集成；界面和功能与原来一致；desktop 的加载和运行速度向社区 VS Code 看齐。外部顾问为此写了一套提示词（项目宪章、阶段任务、角色说明、模板），但看不到内部资料。请收集优化这套提示词所需的信息，整理成不含敏感信息的报告。报告先由负责人审核，再发给顾问。

顾问目前已知的情况（来自早前的方案描述，C1 需要逐条核对）：
- 插件前端使用 Vue 3 + DevUI + Element Plus + vue-i18n + AIhelper。
- 同事的方案：从「iframe + postMessage 的扩展形态」改为「Vue 直接挂载到 Workbench DOM，通过 useService 直连基座 DI 服务」。
- 推进顺序：先迁移后优化；导入插件源码 → 搭建 Bridge 层 → 批量迁移前端 → 加载内核 SDK（kernel）→ 逐个接线 handler → 清理死 handler → 最终修复。
- 已迁移约 65 万行代码。

## 工作要求
1. 只读调查：不修改代码，不提交，不推送。平台能力的小试验在临时目录进行，结束后清理。
2. 这不是正式审计：能较快查到的就查；需要大规模分析、完整构建或长时间运行才能回答的，写【未知】并说明原因。可以引用已有记录，注明记录时间。
3. 不猜测：平台能力和模型参数以平台文档、配置或实际试验为准，不以模型自述为准。交接文档与代码不一致时，以代码为准，并写明差异。
4. 每条回答末尾标注来源：
   【实测】实际运行或试验确认
   【代码】来自代码或构建配置
   【文档】来自交接文档、分析文档或平台文档（注明哪一类）
   【推断】间接推断（写明依据）
   【未知】无法获取（写明原因）
   【需负责人】需要负责人补充或决定
5. 用列表或表格，写数量、类别和结论，不贴大段原文。全文尽量不超过 8000 字；先保证标 P0 的项完整。

## 脱敏规则
不得包含：
- 源代码、配置文件、diff、日志的原文。可以描述结构和类别；确需举例时，用不超过 5 行、去掉内部标识的伪代码。
- 凭证、令牌、密钥、证书、账号。
- 内部域名、URL、IP、端口、服务端点、模型接入地址、内部仓库地址。
- 人员姓名、工号、邮箱。用「迁移负责人」「同事 A」这类角色指代。
- 客户、业务和用户数据；未公开的产品计划。
- CodeMate 专有的提示词、算法或协议细节的原文。
可以包含：
- 已共享过的名称：CodeMate、CodeMate-VSCode、CodeMate-WebView、vscode-internal、kernel（内核 SDK）、AIhelper、交接文档文件名、三个模型路由名和模型标识。
- 开源项目的名称和版本；社区 VS Code 的公开文件路径和 API。
- 数量、比例、耗时、硬件档次（例如「8 核 / 16 GB / SSD」）。
- 泛化后的架构描述、模块类别和问题类型。
内部特有的目录路径只写到说明结构所需的层级。拿不准是否敏感的，换成占位名，并在 K 节列出，交给负责人判断。单条无害、合起来能还原内部系统细节的信息，也要泛化。

## 需要的信息

### A. Agent 平台（决定提示词怎么组织和投放）
A1（P0）平台类型，可以泛化描述。提示词可以通过哪些方式注入：系统提示词、项目规则文件（类似 AGENTS.md）、会话首条消息；各自的长度限制。
A2（P0）子 agent：能否创建；能否为每个子 agent 指定模型；能否真正并行，最多几个；是否共享工作区和文件；结果以全文还是摘要返回，有无长度上限。请做一次小试验：同时创建两个子 agent，分别指定 glm51-critic 和 qwen-security，各在临时目录写一个文件。以平台日志或配置确认实际使用的模型，并记录两者是否并行、父 agent 能否读到这两个文件。
A3（P0）WorkFlow 和 skill：WorkFlow 是什么形式（步骤编排、配置文件、可视化编辑等），能否为每一步指定模型、输入和输出；skill 的文件格式，是常驻上下文还是按需加载。
A4（P0）工具：shell、文件读写、代码搜索、git（建分支、worktree、提交、推送）、MCP、浏览器、启动 desktop 图形界面实例（能否同时运行多个）、后台长时间运行的进程，分别是否可用。
A5（P0）会话：单个会话的时长或轮数上限；上下文用满后如何处理（截断、压缩或报错）；有无跨会话记忆。
A6（P1）权限：能否联网；能否安装 npm 包、skill 或其他工具；能否触发和读取内部 CI。

### B. 模型表现（决定提示词的长度、写法和分工）
B1（P0）用表格列出三个模型各自的：上下文长度、单次输出上限、工具调用是否稳定、名称中「Auto」的含义（例如是否自动切换思考模式）、可调参数、并发、速率和配额限制。
B2（P0）已观察到的典型问题，按模型列出，每条附一个脱敏的简短例子。例如：未验证就宣称完成；中途停下等待确认；忽略长提示词的后半部分；长任务中逐渐偏离目标或忘记约束；编造路径、命令或结果；只总结不动手；擅自扩大修改范围；工具调用格式出错。没有观察记录就写「无记录」。
B3（P1）各模型更擅长和不擅长的任务：读长文档、读写 TypeScript 和 Vue、代码评审、安全分析、中文写作；中文和英文提示词的遵循效果有无差别。

### C. 交接文档（analysis/CodeMate原生DOM集成-交接文档.md）
C1（P0）逐条核对「顾问目前已知的情况」：仍然成立 / 已变化（写明变化）/ 无法确认。
C2（P0）声称的完成情况：按功能或模块统计已完成、进行中、未开始的数量；交接中提到的已知问题、风险、临时绕行方案和未清理的代码。
C3（P1）章节目录；推荐的后续顺序；含糊、互相矛盾或明显过期的地方。

### D. 已有分析
D1（P1）插件分析（analysis/codemate-plugin）、同事方案分析（analysis/y00564605-codemate-dom）、基座能力分析（analysis/ai-native-migration）：各自的主要结论（3–5 条）和对应的代码版本；三者之间、它们与交接文档之间的矛盾。报告中使用前面的简称。

### E. 代码与工程现状
E1（P0）基座：vscode-internal 基于哪个社区 VS Code 版本；对社区文件的改动规模（数量级）；跟随社区升级的方式和频率；社区 Chat 等内置 AI 功能在基座中的状态（保留、禁用或移除）；目标平台（Windows、macOS、Linux）。
E2（P1）界面层：Vue 挂在哪个 Workbench 容器里；是否使用 Shadow DOM，是否还有 iframe；Trusted Types 和 HTML 清洗如何处理；组件库弹层（下拉、对话框、消息提示）挂在哪里；AIhelper 是否大量使用 v-html、是否依赖 webview 特有的 API、是否自带 markdown 和代码高亮库。
E3（P0）逻辑与进程：useService 在哪些层调用（composables、Bridge 层、业务组件）；原插件扩展侧的逻辑迁到了哪里（Workbench 服务、扩展宿主或独立进程）；kernel 在哪个进程加载，使用什么语言和运行时，如何启动，与界面和外部服务之间的通信方式（stdio、HTTP、WebSocket、gRPC 等），是否依赖 Node 内置模块或原生模块，计算负载大致如何。
E4（P1）构建与加载：是否沿用社区构建流程，有哪些自定义；Vue 单文件组件用什么工具编译；CodeMate 代码进入了哪些产物，各自大约多大；在启动时加载还是首次打开时加载。
E5（P0）规模：65 万行这个数字的来源和统计口径；按语言、按类别（业务代码、复制代码、生成物、第三方、测试）的组成，附统计方法；原插件的命令、视图或页面、webview 消息类型、配置项各有多少；主要功能模块列表（名称可以泛化）。
E6（P0）当前状态：能否构建；能否启动；CodeMate 界面能打开到什么程度；主流程（发送请求、流式显示、工具调用）能否走通。可以引用最近一次的记录。
E7（P1）测试与 CI：现有单元、集成、冒烟测试大致覆盖什么；常用的验证命令；agent 能否使用 CI。
E8（P1）协作：同时有多少人或 agent 在改这部分代码；分支和合入流程；文档和工作记录放在哪里。

### F. 性能现状
F1（P1）已有的测量：对照对象（社区版、不含 CodeMate 的基座、原插件、迁移方案）、指标、数值、样本数、方法、机器档次。
F2（P1）用户感知最慢的场景；负责人最关心的指标；是否已有目标值。

### G. 验证工具（zyh/ai-research 中的 VS Code MCP，提交 850e0aa8fcf9a94fc842812924b29b351ccf72e1 → 28356318c067d58bcd89d6857c44db85710ad305）
G1（P0）工具清单：工具名、作用、主要参数和返回值。
G2（P0）连接方式（例如 CDP、Playwright、扩展）；在 agent 平台上能否直接调用；能否指定构建、启动参数、用户数据目录、窗口尺寸；能否截图、读取 DOM、在渲染进程执行脚本、读取性能打点；已知的限制和不稳定之处。

### H. 决策与约束
H1（P0）保留 Vue 是硬性要求，还是可以讨论（例如部分改写为 TypeScript + DOM）？
H2（P0）远程开发（Remote-SSH、WSL、容器）和 Web 版是否在本次范围内？
H3（P1）旧插件的用户数据（会话历史、设置等）需要兼容或迁移吗？
H4（P1）谁做决策（写角色）；哪些事项需要审批；负责人希望在哪些节点看到汇报；agent 的改动是否需要人工代码评审。
H5（P1）启动速度、功能一致、交付范围三者冲突时，按什么优先级取舍？

### I. 已有的 agent 运行经验
I1（P0）是否已用顾问的 v1/v2 或 Codex 版提示词运行过。如果运行过：用了哪部分；产出了什么；哪里做得好；哪里偏离或卡住（附脱敏片段）。
I2（P1）同事迁移过程中使用 agent 的方式和踩过的坑。

### J. 对提示词套件的意见
J1（P1）如果能读到顾问的提示词套件（04-agent-prompt-kit.md，位置由负责人提供）：结合以上调查，指出其中不成立的假设、不适用的要求和缺失的内容，每条附依据。

## 输出格式
# CodeMate 原生化：提示词优化信息（脱敏版）
- 生成模型；调查日期；调查范围（看了哪些资料和代码、做了哪些试验、哪些没看）
## 0. 对提示词影响最大的 5 条发现
## A–J：按上面的编号逐条回答，每条末尾带来源标签
## K. 脱敏说明：做过哪些替换（只写类别和数量，例如「3 处内部路径改为占位名」）；拿不准是否敏感的条目
## L. 待补充：所有标【未知】和【需负责人】的条目编号，方便负责人补充
```

## 四、提示词二：脱敏复核（qwen-security）

```text
# 任务：脱敏复核
下面是一份准备发给外部顾问的信息报告。只检查敏感信息，不评价技术内容，也不改动与脱敏无关的内容。

检查以下类别：
1. 源代码、配置文件、diff、日志的原文；超过 5 行或带内部标识的代码片段。
2. 凭证、令牌、密钥、证书、账号。
3. 内部域名、URL、IP、端口、服务端点、模型接入地址、内部仓库地址。
4. 人员姓名、工号、邮箱。
5. 客户、业务和用户数据；未公开的产品计划。
6. CodeMate 专有的提示词、算法或协议细节的原文。
7. 组合风险：单条无害、合起来能还原内部系统细节的信息。
以下内容已经共享过，可以保留：CodeMate、CodeMate-VSCode、CodeMate-WebView、vscode-internal、kernel（内核 SDK）、AIhelper、交接文档文件名、三个模型路由名和模型标识；开源项目的名称和版本；社区 VS Code 的公开文件路径和 API。

输出：
1. 问题清单：章节编号、类别、原因、建议改法。
2. 修改后的全文：只做脱敏修改。
3. 拿不准的条目：单独列出，交给负责人决定。

报告全文：
{{粘贴信息报告}}
```
